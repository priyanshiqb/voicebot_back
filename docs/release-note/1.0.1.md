# Release 1.0.1

**Released:** 2026-08-14 · **Commits:** `9556f83`, `3d5841a`, plus follow-up fixes

Session and push-notification hardening. Two subsystems that had no retention, no
server-side revocation for devices, and failure paths that reported success while handing
out credentials or alerts that could never work.

> **Backwards compatible.** No endpoint was removed or renamed, no request field became
> required, and no existing response field changed type or disappeared. Every change below is
> either a **new optional field**, a **new status code**, or a **new server-side side effect**.

## Section 1 — What's New

### 🔐 Zero-query session validation

Every authenticated request used to cost one database query against `user_sessions` even on a
cache hit — the cache was saving the `last_used` *write*, not the read. A warm cache now
resolves a token with **no query at all**. Revocation stays instant because every in-code
revocation path writes to the same cache key; the 60-second positive TTL only bounds paths
that bypass `revoke()`, such as an admin edit or direct SQL.

📄 [Authentication — Login, Tokens & Every Authenticated Request](../flows/authentication.md)

### 🧹 Session & JWT blacklist retention

`user_sessions` and SimpleJWT's blacklist both grew forever — with rotation enabled, one
active user writes roughly eight blacklist row pairs per day. A nightly sweep now marks
past-expiry sessions inactive, deletes those beyond `USER_SESSION_RETENTION_DAYS`, and flushes
expired blacklist rows. Session rows hold an IP address and a device name, so this is a
privacy obligation as much as a disk one.

📄 [Maintenance Commands](../commands/README.md) · `purge_expired_sessions`

### 🚦 Sign-in fails loudly instead of silently

If the session row behind a freshly minted token pair could not be written, the three sign-in
paths logged a warning and returned the tokens anyway. Every subsequent request then `401`s —
"login worked, app is broken". All three now return **`503` with no tokens**, which a client
can retry.

📄 [Authentication API](../apiDocs/user/auth.md)

### 🔔 FCM device-token lifecycle

An FCM registration token has no expiry and cannot be validated offline, and **nothing ever
deleted a device-token row**. Reachability is now inferred from how recently the client
re-registered: tokens not seen within `DEVICE_TOKEN_STALE_DAYS` (60) stop receiving pushes,
are demoted by a nightly sweep, and are deleted after `DEVICE_TOKEN_RETENTION_DAYS` (90). A
`--verify` mode asks FCM to confirm a token is dead — a validate-only send that delivers
nothing — before acting.

📄 [Push Notifications (FCM) — End-to-End](../flows/push-notifications.md) · [Device Token Sweep](../commands/purge_device_tokens.md)

### 📡 Push delivery rewritten as multicast

Sends looped one HTTP call per token. They now go out in batches of 500 with per-token
results, and failures are **classified** rather than uniformly logged: FCM disowning a token
retires it immediately, quota and outage errors leave it completely alone, and an ambiguous
`INVALID_ARGUMENT` takes one strike. When an entire batch fails the same ambiguous way the
message is blamed instead of the devices — a distinction only a batched send can make.

📄 [Push Notifications (FCM) — End-to-End](../flows/push-notifications.md)

### ⏱️ Push messages now expire, collapse and deep-link

Every push carries a TTL (`PUSH_TTL_SECONDS`, 24h), a collapse key, an explicit priority, and
iOS `content-available` for data-only messages. A "booking needs rescheduling" alert arriving
three days late is worse than none, so it is now dropped instead. Notifications also carry
`data.route` for deep-linking, and on web that becomes a real click target.

📄 [Device Tokens API — Handling a notification](../apiDocs/core/device_token.md)

### 📓 Push is recorded and retried like email

`NotificationLog` carried an `FCM` channel that no production code ever wrote — pushes had no
dedup key, no audit row, and no retry. Each push now writes a deduplicated `FCM` row and the
tasks retry with backoff. Zero acceptances is recorded `FAILED`, not `SENT`, so it stays
re-enqueueable.

📄 [Flow 5 — Notifications & Push](../flows/05-notifications-and-push.md)

### 🔗 Sessions own push devices

A device token now records the login session it registered under, so the death of that session
silences the device. This closes the one path no client can close for itself: when a refresh
token **expires**, the app has no credentials left to call any endpoint with, yet its device
kept receiving alerts with nobody signed in.

📄 [Push Notifications — The session link](../flows/push-notifications.md) · [Sessions API](../apiDocs/user/sessions.md)

### 🛡️ Device registration limits

Registration is rate-limited per user (`DEVICE_TOKEN_REGISTER_RATE`, default `60/hour`) and
each user is capped at `DEVICE_TOKEN_MAX_PER_USER` (20) live devices per tenant, oldest
retired first. The throttle applies to the register action only — reading your device list is
not limited.

📄 [Device Tokens API — Limits on registration](../apiDocs/core/device_token.md)

### 🧪 Push self-test endpoint

`POST /core/device-tokens/test/` sends a real notification to your own devices and reports
what happened to each. It exists because every other signal was ambiguous: registration
returning `201` proves the token was *stored*, never that a notification will arrive.

It separates the failure modes instead of collapsing them into one "0 sent" — push disabled
server-side, credentials that will not load, no deliverable device, or FCM rejecting a
specific handset — so you debug the right thing. Passing `token` sends to that exact string
verbatim, with no device lookup and no staleness rule, for testing a token the app has just
produced.

📄 [Device Tokens API §4b](../apiDocs/core/device_token.md)

### 🔑 Firebase credentials: inline JSON, and loud misconfiguration

`FIREBASE_CREDENTIALS` now accepts **either** a path to the service-account JSON **or** the
JSON itself. Pasting the file's contents into the variable is the obvious thing to try and
previously blew up inside `Certificate()` complaining about a filename — which meant push
was silently, completely broken on any deployment that did it.

A credential that is set but unusable is now a distinct, reported state rather than an
exception raised through every send. Blank still means "push is off here" and stays quiet.

📄 [Firebase / FCM setup](../external-app-creds/01-firebase-fcm.md)

### 🛠️ Device-token admin actions

The `Device Token` admin gained **Send a test notification** and **Validate the token(s) with
FCM** (a probe that delivers nothing). The API endpoint only ever targets the caller's own
devices, which is useless when the question is why *somebody else's* handset is silent. Both
actions share the endpoint's code, so the two cannot drift. The list now also shows
`last_error`, `failure_count` and a truncated token.

Used together they localise the fault: **accepted + alive means the problem is on the
device**, not the server.

📄 [Device Tokens API](../apiDocs/core/device_token.md)

### 🔒 Documentation portal requires a password

The developer docs served on `DOCS_PORT` (default 8088) are now behind HTTP basic auth,
enforced **inside the container** rather than at the gateway — the port is published straight
onto the host, so a gateway rule would have protected `docs.<domain>` and left the port open.
Credentials default to `GATEWAY_BASIC_AUTH_*`, so existing deployments keep working.

📄 [Command Runbook §3b](../runbook.md)

### 📕 Command runbook

A single reference for setup, compose profiles, the test invocation (and the two flags you
must pass), migrations, all 13 management commands, schema generation, and the failures that
look like bugs but are not.

📄 [Command Runbook](../runbook.md)

## Section 2 — Endpoint Changes

One endpoint is new; nine changed. Request-field and response-field changes are called out
explicitly; everything else is a new status code or a new server-side side effect.

<!--copy:start id="ep-device-test" label="Copy"-->
### `POST /api/v1/core/device-tokens/test/` 🆕

**New endpoint.** Sends a real test notification to your own devices and reports the outcome
of each.

| | |
|---|---|
| Request field | `token` *(string, optional)* — send to this **exact** token, verbatim: no device lookup, no ownership requirement, no staleness rule. Omit to fan out to every device registered to you |
| Auth | JWT required. Agent (`VB_AGENT`) tokens are `403` like the rest of this viewset |
| Rate limit | **None.** A limit bites hardest while push is still being wired up |

**Response `data`:**

| Field | Type | Meaning |
|---|---|---|
| `push_enabled` | boolean | Whether `FIREBASE_CREDENTIALS` is set at all |
| `configuration_error` | string \| null | Set but unusable — why the credential failed to load |
| `registered` | integer | Your non-deleted devices, **including** inactive and stale ones |
| `targeted` | integer | How many we actually attempted |
| `accepted` | integer | How many FCM took |
| `results[].id` | uuid \| null | Null when the token is not a device you registered |
| `results[].platform` | string \| null | |
| `results[].last_seen_at` | datetime \| null | |
| `results[].known_device` | boolean | False ⇒ sent to the string you supplied, but no row exists, so it will never receive a *real* notification |
| `results[].accepted` | boolean | FCM took it |
| `results[].detail` | string \| null | Why it was not accepted |
| `results[].deactivated` | boolean | The attempt retired this device |

**Status codes are deliberately distinct** — a single "0 sent" cannot tell a switched-off
server from a broken handset:

| Status | When |
|---|---|
| **200** | An attempt was made; `results` says what each device did |
| **400** | No deliverable device. `registered: 0` = none at all; `registered > 0` = all inactive or stale |
| **503** | `push_enabled: false` — not configured on this server |
| **503** | `configuration_error` set — configured but the credential will not load |

> ⚠️ **`accepted: true` is not delivery.** It means FCM took the message; the send API issues
> no per-device receipt. On **web** in particular, a message delivered while the registering
> page is *visible* goes to your `onMessage` handler and is **not** displayed by the browser —
> if your app does not render it, nothing appears even though everything succeeded.

### `POST /api/v1/auth/login/`

**Change:** new `503` response.

| | |
|---|---|
| Request fields | *unchanged* |
| Response fields | *unchanged* |
| New status | **`503`** — `"Could not start a session. Please try again."` |

The session row is now written atomically with the `last_login` stamp. If that write fails,
the endpoint returns `503` **with no tokens** instead of returning a pair that would `401` on
every subsequent call. **Client action:** treat `503` as retryable; do not sign the user out.

### `POST /api/v1/auth/refresh/`

**Change:** new `503` response.

| | |
|---|---|
| Request fields | *unchanged* |
| Response fields | *unchanged* |
| New status | **`503`** — `"Could not refresh the session. Please log in again."` |

Returned when the tokens rotate but the session row cannot be updated. **This one is
terminal, unlike login's `503`:** rotation has already blacklisted the refresh token you sent,
so the client must log in again rather than retry.

### `POST /api/v1/onboard/verify/`

**Change:** new `503` response.

| | |
|---|---|
| Request fields | *unchanged* |
| Response fields | *unchanged* |
| New status | **`503`** — `"Your payment was successful and your account is ready, but we could not sign you in automatically. Please log in to continue."` |

<!--copy:start id="ep-logout" label="Copy"-->
### `POST /api/v1/auth/logout/`

**Change:** new optional request field + new side effect.

| | |
|---|---|
| **New request field** | `device_token` *(string, optional)* — the FCM registration token of the device signing out |
| Response fields | *unchanged* |
| Statuses | *unchanged* |

Supplying `device_token` deactivates that device so pushes stop reaching it. Matched against
**your own** tokens only; naming someone else's silently does nothing, and unknown values are
ignored. Deactivation is best-effort — if it fails the logout still returns `200`.

**Client action:** on sign-out, call the Firebase SDK's `deleteToken()` **and** pass the token
here. Deactivating server-side alone leaves the device subscribed at Google.

> Since the session↔device link shipped in the same release, forgetting this field no longer
> leaves the device subscribed — `revoke()` catches it. The field is now a fast path, not the
> only mechanism.

📄 [Authentication API — Logout](../apiDocs/user/auth.md)

<!--copy:start id="ep-device-register" label="Copy"-->
### `POST /api/v1/core/device-tokens/`

**Change:** new `429`, new response field, new limits, new side effects.

| | |
|---|---|
| Request fields | *unchanged* (`token`, `platform`) |
| **New response field** | `last_error` *(string)* — why the device was last deactivated; `""` when healthy |
| **New status** | **`429`** — more than `DEVICE_TOKEN_REGISTER_RATE` (default `60/hour`) registrations by this user. Honour `Retry-After` |

Additional server-side behaviour on every successful registration:

- **Links the device to your current login session.** The link moves to the newest login on
  re-registration, so revoking an older session cannot silence a device in active use.
- **Clears the send-side verdict** — `last_error` is emptied and the internal consecutive
  failure count resets to `0`. This is the self-heal path.
- **Enforces the per-user cap** (`DEVICE_TOKEN_MAX_PER_USER`, default `20` live devices per
  tenant). The oldest are deactivated; the device you just registered is never the one
  retired. This succeeds silently — it is not an error.
- **Resets the staleness clock.** A token not re-registered within `DEVICE_TOKEN_STALE_DAYS`
  (60) stops receiving pushes and is later deleted.

⚠️ **On web, registering on every app start is now mandatory rather than advisable.** The JS
SDK v9+ has no `onTokenRefresh` callback, so a client that skips it never reports a rotated
token *and* ages out — going dark with no error anywhere.

### `GET /api/v1/core/device-tokens/`

**Change:** new response field.

| | |
|---|---|
| Query parameters | *unchanged* |
| **New response field** | `last_error` *(string)* — added to each row in `data[]` |

`is_active: false` no longer means one thing. `last_error` distinguishes the seven causes:
`""` (deactivated via the API), `Signed out on this device`, `Session ended`,
`FCM rejected the token: …`, `INVALID_ARGUMENT: … x3`, `Not re-registered in 60 days`, and
`Exceeded 20 active devices`.

The list still omits the raw `token` string — that is returned only by register and retrieve.

### Behaviour changes with no endpoint signature change

| Area | Change |
|---|---|
| Push audience | Sends now target only **deliverable** tokens — active, not deleted, **and** re-registered within `DEVICE_TOKEN_STALE_DAYS`. A token can read `is_active: true` and still be skipped |
| Refresh-token expiry | The device registered under an expired session is deactivated by the nightly sweep. No client call is involved — an expired refresh token leaves the app with no credentials to make one |
| Push retries | Push tasks retry with backoff (`max_retries=3`) and write a `NotificationLog` row; a push accepted for zero devices is recorded `FAILED`, not `SENT` |
| Firebase credentials | A credential that is set but unloadable no longer raises through every send. It is caught, logged at error level, and reported as `configuration_error` |

## New settings

All optional — every one has a working default.

| Setting | Default | Effect |
|---|---|---|
| `USER_SESSION_RETENTION_DAYS` | `30` | How long an expired session row is kept, from expiry |
| `USER_SESSION_PURGE_BATCH` | `5000` | Rows deleted per chunk by the session sweep |
| `SESSION_CACHE_TTL_SECONDS` | `60` | Positive session-check cache; bounds revocation latency for paths bypassing `revoke()` |
| `DEVICE_TOKEN_STALE_DAYS` | `60` | No re-registration in this window ⇒ the token stops receiving pushes |
| `DEVICE_TOKEN_RETENTION_DAYS` | `90` | How long a dead device row is kept, from last contact |
| `DEVICE_TOKEN_MAX_PER_USER` | `20` | Cap on live registrations per user per tenant |
| `DEVICE_TOKEN_FAILURE_STRIKES` | `3` | Ambiguous send failures before a token is retired |
| `DEVICE_TOKEN_PURGE_BATCH` | `5000` | Rows deleted per chunk by the device sweep |
| `DEVICE_TOKEN_REGISTER_RATE` | `60/hour` | Per-user rate limit on device registration |
| `PUSH_TTL_SECONDS` | `86400` | How long FCM keeps retrying before dropping a push |
| `DOCS_BASIC_AUTH_USER` | `GATEWAY_BASIC_AUTH_USER` | Login for the documentation portal |
| `DOCS_BASIC_AUTH_PASSWORD_HASH` | `GATEWAY_BASIC_AUTH_PASSWORD_HASH` | bcrypt hash — **double every `$`** in `.env` |
